# ADR-020: Build an Offline Benchmark Harness That Separates Regression From Methodology Failure

- Status: Proposed
- Date: 2026-11-01
- Decision owners: Project owner (implementation delegated; owner review pending)
- Related: ADR-001, ADR-009, ADR-010, ADR-018, ADR-019, ADR-022

## Context

`docs/evaluator/BENCHMARKING_AND_VALIDATION.md` states what validation requires and is honest that
none of it has been done. Local core v0.2 shipped with 335 tests, all of which check that the
software does what the code says. None of them check that the evaluator's *judgements* match what
careful human reviewers conclude. Those are different questions, and passing the first does not
address the second.

Without a harness, two failure modes are indistinguishable in practice:

- **Software regression.** The evidence-aggregation rule, a metric formula, or an input validator
  changed behaviour. The correct response is a code fix.
- **Methodology failure.** The rule and the metric are implemented faithfully, but a human
  reviewer disagrees with the verdict they produce. The correct response is a methodology change
  and a new metric version, never a code patch.

Building the harness is straightforward. The hard part is honesty about its inputs: a gold set can
only come from real material that a human actually reviewed and that the operator is authorised to
store. Nothing in this milestone authorises inventing cases, and an invented gold set is worse than
no gold set because it produces confident, meaningless numbers.

## Decision

1. **A versioned case contract, not an ad-hoc fixture.** `src/benchmark/cases.ts` defines
   `benchmark-case-v1`: a case has an identifier, a stratum, provenance, the frozen input pack
   (claim revision text, propositions, recorded evidence relationships with their reviewer-recorded
   relations, an optional captured answer with citations), the expected labels per scored dimension,
   optional per-reviewer labels with an adjudication record, and a limitation note. Case files are
   JSON validated by code, not by convention.
2. **Four scored dimensions, matching the product's separation.** Evidence support, answer fidelity,
   citation support, and attribution are scored independently. There is no overall benchmark score,
   and a case may be scored on any subset. A dimension with no eligible expected label is reported
   as not scored, not as zero cases passed.
3. **Strata are a validation requirement, not a wish list.** The validator requires declared
   coverage for the strata that matter most for anti-gaming: supported, partially supported with
   conditions, contradicted, conflicting, insufficient evidence, unavailable/inaccessible, refusal
   that is not a denial, attribution with wrong role, false sole credit, citation that does not
   support, citation that supports only under conditions, and multi-subclaim mixtures. A corpus
   missing a stratum reports which strata are absent; it does not pass.
4. **Deterministic regression scoring is distinct from methodology scoring.** Two scorers exist:
   - `scoreRegression` runs the *current* implementation over each case's frozen input pack and
     compares the produced verdict with the case's expected label. Any mismatch is a candidate
     software regression and names the rule, metric, or validator involved.
   - `scoreMethodologyAgreement` compares gold labels against each other (reviewer-to-reviewer and
     reviewer-to-adjudicated-gold) and reports per-class precision, recall, F1, support, a confusion
     matrix per dimension, and macro-F1 where every class has support.
   A case can therefore fail for one reason and pass for the other, and the report keeps them in
   separate sections.
5. **Measures are computed only over what exists.** Precision, recall, F1, and support are reported
   per label; confusion matrices are reported only when the dimension has at least two labels
   present. Macro-F1 is reported only when every class in the label set has at least one gold
   example, and is reported as `null` with a reason otherwise. Agreement statistics are computed
   only when a case carries two or more independent reviewer labels.
6. **No statistical claims without a justified basis.** The harness does not compute confidence
   intervals, calibration, or significance. It emits an explicit statement that sample sizes are
   purposive and that aggregate accuracy over a small curated corpus must not be generalised. A
   future interval requires its own ADR with method and sample justification.
7. **Reviewer identity is declared, not authenticated.** Reviewer fields are operator-asserted
   labels. The report must state that "two reviewers" means two locally entered labels and is not
   proof of independent review, because local core has no authentication.
8. **Gold content is never generated by the harness.** The code validates structure and scores
   supplied material. It contains no fabricated achievements, sources, people, or answers. Corpus
   files live outside the application database, so benchmark material cannot appear as project data
   or leak into reports.
9. **Synthetic cases live only in tests.** Unit and integration tests may construct cases in memory
   to prove the harness works. A test-created case must never be written into a distributed corpus
   directory, and the runner refuses a corpus entry whose provenance is not human-reviewable.
10. **Corpus provenance is mandatory and rendered.** Each case carries `provenance` with the source
    of the material, whether it is authorised for storage, who reviewed it, when, and what remains
    unverified. The report includes a provenance summary, and any case lacking it is reported as a
    validation error rather than scored.
11. **Reproducible report artifact.** `npm run benchmark -- --corpus <dir>` emits a JSON report with
    the corpus file digests, corpus size and composition, the methodology and metrics versions used,
    per-dimension results, confusion matrices, strata coverage, disagreement and adjudication
    summary, and the limitation statement. Running it twice on the same inputs produces identical
    bytes; nothing depends on wall-clock time or random ordering.
12. **Empty corpus is a truthful result, not a pass.** With no cases, the runner exits with a
    non-zero status and prints that no accuracy claim is supportable. It must not report 100% or 0%.
13. **A new module layer.** The harness lives in `src/benchmark/`, which may import `core` and Node
    builtins only, and must not import `persistence`, `reporting`, `app`, or `website`. See ADR-022.

## Alternatives considered

1. **Judge Aporia's verdicts with an LLM.** Rejected: prohibited by the milestone scope, and it
   would make the thing being validated responsible for the validation.
2. **Treat the existing 335 tests as validation.** Rejected: they are implementation-conformance
   tests. A test that encodes the current rule's behaviour cannot detect a methodology error.
3. **One blended benchmark score.** Rejected by ADR-003; it would hide which dimension failed.
4. **Ship a starter corpus of plausible-looking synthetic cases.** Rejected: this is the central
   honesty risk. Synthetic material presented as gold labels would produce a fabricated accuracy
   claim, which the milestone explicitly forbids.
5. **Store benchmark cases in the application database.** Rejected: benchmark material would appear
   in project views and could be pulled into reports.
6. **Compute confidence intervals over small corpora for completeness.** Rejected: unjustified
   precision is worse than an acknowledged gap.
7. **Score only agreement and skip regression comparison.** Rejected: without the deterministic
   section, a code change and a rubric change look identical.

## Consequences and trade-offs

- The harness exists and produces honest numbers only when someone supplies real reviewed material.
  Until then, the correct public statement is "framework implemented, validation not performed".
- Requiring strata makes small corpora fail loudly. That is the intent; silent under-coverage is how
  a benchmark becomes theatre.
- Two scorers mean two reports for one run, and a reader must understand which question each answers.
  The report labels both explicitly.
- The JSON contract is now a compatibility surface. Changing case semantics requires a new
  `benchmark-case-vN` and a documented migration.

## Security, privacy, safety, and evaluator-validity implications

- Case files may contain sensitive claims and evidence excerpts. They are operator-managed local
  files, are not uploaded anywhere, and the corpus directory should be treated with the same care as
  the database file.
- Corpus input is untrusted data. The loader enforces a file-size cap, a case-count cap, strict
  field validation, and refuses unknown versions; malformed input produces a validation error, never
  a crash and never a partial score.
- Nothing in the harness reaches the network. The repository's no-network guard applies.
- Benchmark output must not be quoted as an accuracy claim without the corpus size, composition,
  provenance, and limitations that accompany it.

## Implementation plan

1. `src/benchmark/types.ts` — the `benchmark-case-v1` contract and result types.
2. `src/benchmark/validate.ts` — structural and semantic validation, strata coverage.
3. `src/benchmark/scoring.ts` — per-label counts, precision/recall/F1, confusion matrices, macro-F1
   with support gating, agreement statistics.
4. `src/benchmark/regression.ts` — run current rule/metric implementations over frozen input packs.
5. `src/benchmark/report.ts` — deterministic report assembly with digests and limitations.
6. `scripts/benchmark.ts` + `npm run benchmark` — corpus loading with bounds and the CLI.
7. `docs/evaluator/BENCHMARK_ANNOTATION_RUBRIC.md` — the labelling procedure tied to the vocabulary.
8. Boundary checker update for the new layer.

## Tests and validation required

- A well-formed single case validates; each structural defect produces its own named error.
- Missing strata are reported as missing, and a corpus cannot pass without declaring them.
- A deliberately mismatched expected label is reported as a regression candidate, not an agreement
  failure.
- Reviewer disagreement with no adjudication is reported as unresolved, not averaged.
- A dimension with one class present yields `null` macro-F1 with a stated reason.
- Empty corpus, malformed JSON, oversized file, unknown version, and missing provenance all fail
  with explicit errors.
- Two runs over the same corpus produce byte-identical reports.
- No benchmark code imports persistence, reporting, app, or website; the boundary check enforces it.
- `tests/unit/no-network.test.ts` continues to pass with the harness present.
